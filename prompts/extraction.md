# 四阶段结构化识别流程

本 Prompt 与 `topology_recognition` Skill、调用方提供的阶段任务和目标 JSON Schema 共同使用。
调用方在当前任务中指定 `currentStage` 或 `stage`。只执行该阶段对应的规则，不补做其他阶段，也不输出阶段过程说明。

## 共享输入与输出规则

1. 读取当前阶段、`taskId`、图片尺寸、当前视图信息、调用方提供的稳定对象摘要和目标 JSON Schema。
2. 只加载本次请求中的 `topology_recognition` Skill，不假设另两个 Skill 已加载。
3. 视觉阶段只使用当前请求提供的一张完整图片；`fusion` 阶段应确认没有图片输入。
4. 只输出目标 Schema 定义的字段。调用方负责稳定 ID、坐标转换、确定性预融合、补丁应用、最终统计和一致性校验。
5. 保留 `rawText` 或等价原文字段、有限候选、置信度、Evidence 和未解析项，不用单一答案掩盖歧义。
6. 不从 `viewId`、文件名、任务标识、图片尺寸或哈希推导拓扑答案。
7. 不生成随机 UUID，不引用当前任务中不存在的稳定对象 ID。
8. 视觉阶段的 `temporaryModelId` 必须使用 `tmp_` 开头的本响应内唯一标识，不得伪装成程序保留的 `Nxxx`、`Rxxx`、`obs_*`、`evidence_*`、`unresolved_*` 或 `conflict_*`。

## 视觉阶段通用规则

- 当前图片覆盖完整拓扑。先建立整体空间关系，再按当前阶段目标观察，不改变图片中对象的位置。
- 坐标使用当前完整视图像素，并以图片中心为原点 `(0,0)`：x 向右、y 向下，左侧和上方坐标可为负数；所有 `Point` 的 `x/y` 和 `BoundingBox` 的 `x/y/width/height` 最多保留两位小数，不得归一化。`bbox` 必须完整位于当前视图内且有正面积，`center` 应位于对应设备主体 `bbox` 内。
- `structure` 的每个节点先按目标检测定位设备图标主体，再填写 `bbox`；框只覆盖图标可见主体的紧致外接矩形，不包含节点名称、接口名、IPv4、连线、区域边框或邻近空白。`center` 必须是该图标框的几何中心，不是文字中心。
- 定位时先在中心原点像素坐标中确定 `bbox_2d=[x1,y1,x2,y2]`，再写入当前 Schema：`x=x1`、`y=y1`、`width=x2-x1`、`height=y2-y1`；不要把 `x2/y2` 直接填入 `width/height`。
- 输出前逐个复核：框的四条边应贴近图标实际边缘，图标应位于框内部且不只占框的一角；若只能定位到文字而不能定位主体，保留低置信度或未解析项，不要用文字位置代替设备位置。
- `polyline` 至少包含两个点，并按可见路径顺序记录所有必要折点。
- 不因图片分辨率、视觉密度或对象数量要求追加模型调用。
- Evidence 必须描述实际看到的内容。其真实来源由调用方按当前阶段登记；仅当目标 Schema 包含 `sourceViewId` 时才输出该字段，且取值只允许：
  - `global_structure`：设备主体、粗粒度类型、区域框及其邻近文字；
  - `global_links`：连线、端点、折点和交叉状态；
  - `global_text`：节点名、接口名、IPv4、前缀和区域标题。
- `VISUAL_TEXT` 只用于可见文字，`VISUAL_ICON` 用于设备主体，`VISUAL_LINE` 用于连接线，`VISUAL_REGION` 用于区域，`MODEL_INFERENCE` 用于非直接文字的模型判断。
- Evidence 的 `bbox` 只覆盖相关可见内容且宽高必须都大于 0。竖直线或水平线也应把可见线宽包入正面积框，不得用宽度或高度为 0 的退化框。除 `MODEL_INFERENCE` 外，Evidence 必须提供 `bbox` 或 `rawText`；`MODEL_INFERENCE` 可以只有描述和置信度，因为它表达的是非直接文字的判断。不得引用未在当前响应中表达的 Evidence，也不得在 Schema 未定义时自行增加 `sourceViewId`。
- 每条 Evidence 必须显式输出 `confidence`，取值与该证据本身的清晰度相符；不得省略该字段。
- 每个视觉观察通常只输出一条紧凑 Evidence；只有文字与图标等证据类型确实不同才输出第二条。`description` 使用短句，不重复阶段任务或对象全部字段。
- 模糊字符如 `0/O`、`1/l/I`、`5/S` 应保留有限合理候选；无法看清的字符保留在原文中，不静默改写。
- 置信度按证据质量区分：清晰直接证据使用 `0.90–1.00`，轻微遮挡或折线使用 `0.75–0.89`，多个合理候选使用 `0.50–0.74`，局部或无法确定的证据低于 `0.50`；不要为所有对象复用同一个常数。
- `text` 阶段保持增量且紧凑：currentTopology 已有的节点名、区域名和链路阶段接口名不要重复输出；每个节点最多一个 `interfaceObservation`，其中可用多行 `rawText` 表达该设备周围全部接口/IP 事实。接口候选和 IPv4 候选必须逐项拆分，`rawText` 事实块不超过 4096 个字符，每个候选字段最多 128 个去重值，每个事实块通常只保留一条 Evidence；不得输出长篇解释。
- 区域不是节点，区域边框不是链路，普通文字、IP 和接口标签也不是节点。
- 两条线几何相交不自动表示连接；没有连接标记时保留交叉歧义。

## 阶段一：structure

输入图片必须是 `global_structure`。本阶段只输出设备节点和区域的视觉候选。

### 必须观察

- 所有具有可见设备主体的节点候选；
- 每个设备主体的 `bbox` 和 `center`；
- 粗粒度语义类型候选；
- 节点附近的原始名称候选；
- 区域边框、区域 `bbox` 和粗略名称候选；
- 低置信度、遮挡或无法判断的对象；
- 支撑每项观察的 Evidence。

### 输出纪律

- `temporaryModelId` 只需在本响应中唯一；调用方会按几何位置重新分配 `Nxxx` 和 `Rxxx`。
- 节点 `bbox` 只包围设备主体，不包含大范围连线或无关文字。
- 名称候选保留图片原文；类型不明确时列出候选或使用 `unknown`。
- 区域成员关系不明确时只提出候选，不强制归属。

### 不执行

- 不恢复完整链路；
- 不识别精确接口或 IPv4；
- 不计算网络地址、网关或广播域；
- 不生成最终 Observation ID 或平台字段。

## 阶段二：links

输入图片必须是带稳定节点和区域编号的 `global_links`。本阶段只输出可见链路和新增节点候选。

### 必须观察

- 主要物理或逻辑连线；
- 输出 JSON 前逐一复核图片中每条可见连接线，确保分析文字中提到的链路都出现在 `links` 数组；不得只在推理过程提及而遗漏结构化对象；
- 每条链路的源、目标节点候选；
- 可见路径的 `polyline`；
- 一对多扇出、连接点和交叉状态；
- Pass 1 可能遗漏的设备主体；
- 端点歧义和支撑链路的 Evidence。

### 引用纪律

- 端点优先引用调用方摘要中的 `Nxxx`，区域引用使用已有 `Rxxx`。
- 不得引用摘要中不存在的稳定编号。新增节点先作为 `additionalNodeCandidates` 输出，不自行创建 `Nxxx`。
- 无法确定端点时保留多个候选或空候选并创建未解析项，不随机选择唯一端点。
- 区域矩形、图标轮廓、装饰线和文字下划线不得作为链路。
- 交叉处只有在存在实心点、汇聚符号或清晰接头时才可作为连接证据。
- 编号设备是链路终点，不是可穿过的折点。两段线在编号设备处相接时，分别输出到该设备的两条链路；不得把它们沿完整路径拼接成跨越该设备的直接链路。只有路径中不存在第三个编号设备时，连续多段折线才属于同一条链路。

### 不执行

- 不读取完整接口配置或精确 IPv4；
- 不推断网络、网关、广播域或平台链路；
- 不要求重绘图片或再次执行本阶段。

## 阶段三：text

输入图片必须是仅做过一次保守文字增强的 `global_text`。本阶段只输出可见文字及其归属候选。

### 必须观察

- 节点名称和节点编号候选；
- 接口名称；
- IPv4 原文和合法读数候选；
- 可见前缀长度候选；
- 接口、IPv4 与节点或链路的空间邻近关系；
- 区域标题及区域编号候选；
- 无法可靠绑定的文字和对应 Evidence。

### 增量输出约束

- `currentTopology` 中已存在的节点名称、区域标题和链路阶段接口标签是已知事实；除非发现更清晰的修正，不要再次输出。
- `interfaceObservations` 按节点分组，而不是每个物理端口一个 JSON 对象。一个观察可用多行 `rawText` 表达多个接口，每行使用 `<接口> <IPv4/前缀>` 或 `<接口>`。
- 每个可见 IPv4 和前缀都必须出现在对应接口事实行、`ipv4Candidates` 或 `prefixLengthCandidates` 中；不能为了缩短响应删除地址。
- `checkedNodeIds` 仍必须覆盖全部节点，`textCoverageComplete` 只在完成清点后设为 `true`。

### 保守文字规则

- `rawText` 保留图片可见原文，即使其中含有 `?` 或相似字符歧义。
- 接口名候选、IPv4 候选和前缀候选分别表达，不根据厂商习惯或同网段常识补齐。
- 裸 IPv4 不得自动补前缀；模糊 IPv4 不得静默改成某个合法地址。
- `labelBBox` 只覆盖接口名、节点名或区域标题；`ipBBox` 只覆盖 IPv4 或前缀文字。
- 文字可属于多个节点、区域或链路时，保留全部合理稳定 ID 候选，不强制绑定。
- 节点名称、接口名称和 IPv4/前缀必须分开输出；`名称\\nIP/前缀` 不能作为新的节点名称候选。
- 逐个检查输入中的每个节点。对于 `router`、`firewall`、`switch_l3`，列出设备周围全部可见接口名称及对应 IP/前缀；一个设备可以有多个接口。
- 对客户端、服务器和 VPC 节点，只要看到 `eth0` 或 IP 标签，也必须形成接口观察。
- IP 必须绑定到接口候选；关系不确定时保留接口/IP 候选，不得删除可见地址。
- 返回 `checkedNodeIds` 和 `textCoverageComplete`，前者必须覆盖调用方 `currentTopology.nodes` 中的每个节点；未完成时将 `textCoverageComplete` 设为 `false`。

### 不执行

- 不计算网络地址、默认网关或重复 IP；
- 不完成接口、IP、节点或链路的最终归属；
- 不生成完整 `TopologyObservation`、网络推理结果或平台字段。

## 阶段四：fusion

本阶段是对三个视觉阶段结构化结果的纯文本语义融合。输入不得包含图片或图片编码；即使 `conflicts` 是 `[]` 也必须返回合法补丁对象，其中 `decisions` 为 `[]`。

### 输入边界

- 只使用输入中的稳定对象 ID、候选、Evidence 摘要、空间上下文、`conflictId` 和 `candidateIndex`。
- 不重新识别图片，不从缺失信息推导新视觉事实。
- 不使用与冲突无关的文字扩写上下文。

### 允许的裁决

- `SELECT_CANDIDATE`：证据足以支持输入中的唯一候选索引；
- `KEEP_MULTIPLE_CANDIDATES`：多个输入候选仍合理；
- `MERGE_OBJECTS`：输入冲突明确允许且证据支持对象合并；
- `KEEP_OBJECTS_SEPARATE`：证据支持对象独立；
- `BIND_REFERENCE`：证据支持输入中已有对象间的引用；
- `LEAVE_UNRESOLVED`：证据不足以安全裁决。

### 补丁纪律

- 每个 decision 必须引用输入中存在的 `conflictId`。
- `selectedCandidateIndexes` 只能包含该冲突现有的 `candidateIndex`。
- `SELECT_CANDIDATE` 和 `BIND_REFERENCE` 必须且只能提供一个候选索引；其他 action 可使用空数组，或仅列出其需要保留的现有候选索引。
- 不得返回未知对象 ID，不得重新编号或修改稳定 ID。
- 不得修改 `bbox`、`center`、`polyline`、Evidence、`sourceViewId` 或原始候选。
- 不得创建或删除节点、接口、链路、区域、Evidence 或未列出的事实。
- 不得直接输出最终 `TopologyObservation`，不得输出 summary。
- `reasonCode` 使用简短的受控大写下划线字符串，不输出长篇自然语言解释。
- 证据不足时选择 `KEEP_MULTIPLE_CANDIDATES` 或 `LEAVE_UNRESOLVED`，不得为了完整性消除所有歧义。
- 不把 `NAME_PLUS_IP`、规范化差异或包含关系当作名称冲突；接口尚未物化也不等同于链路节点端点歧义。
- 只裁决真正互斥的已有候选，不创建新的接口、节点、链路、Evidence 或坐标，也不修改稳定 ID。

## 未解析项与置信度

- `0.90` 到 `1.00` 仅用于证据清楚且一致的观察。
- `0.75` 到 `0.89` 表示主要事实可靠但仍可能有细节误差。
- `0.50` 到 `0.74` 表示存在明显歧义。
- 低于 `0.50` 的观察不得伪装成自动可采用的事实。
- 对模糊名称、类型、端点、文字归属、接口归属、IP 归属或区域归属保留候选并创建适用的未解析项。
- 不通过删除候选、Evidence 或未解析项制造完整结果。

## 输出前内嵌自审

在内部检查但不要输出审计说明：

1. 当前响应是否只完成当前阶段职责；
2. 所有字段、枚举、ID 形状和集合是否符合目标 Schema；
3. 所有引用是否指向当前任务或当前响应中存在的对象；
4. 所有视觉坐标是否位于当前完整视图内；
5. Evidence 类型、`sourceViewId`、`bbox` 和原文是否与事实一致；
6. 是否错误地把区域、普通文字或交叉线当成节点或连接；
7. 是否保留了原文、候选值、置信度和不确定性；
8. 是否包含网络推理、平台字段、样例答案或图片不可见事实；
9. `fusion` 是否仅输出已有冲突的补丁，且未修改几何或 Evidence；
10. 自审完成后只输出一个符合 Schema 的 JSON 对象。
